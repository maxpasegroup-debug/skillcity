# AIRA Technical Debt Register

| Issue | Domain | Severity | Why it exists | Impact | Recommended action | Timing |
|---|---|---:|---|---|---|---|
| Production DB state and data normalization unknown | Database | Critical | No `DATABASE_URL` was available during Phases 1-12 | Schema/data incompatibility can break launch | Run migration and normalization runbooks with backup | Before launch |
| Backup/restore and disaster recovery unproven | Operations | Critical | Provider evidence is outside repository | Data loss may be unrecoverable | Test snapshot restore; set RPO/RTO and ownership | Before launch |
| Public status uses WhatsApp number alone | Admissions/privacy | Critical | Convenience flow predates stronger verification | Account/application existence, program and status can be enumerated | Add OTP or opaque application secret; otherwise disable | Before public launch |
| Process-local rate limiting | Security | High | Phase 0 used an in-memory map; `REDIS_URL` is not wired | Limits reset/restart and differ per replica | Use shared store or edge/WAF controls with trusted client IP policy | Before broad traffic |
| Payment provider reference has no DB unique key | Finance | High | Duplicate check is application-level only | Concurrent requests can record duplicates | Add reviewed nullable uniqueness/idempotency migration | Before concurrency/webhooks |
| Private object storage/download absent | Documents | High | Phase 8 intentionally implemented metadata only | Private files cannot be safely uploaded/served | Implement approved provider, signed access, scanning and limits | Before private documents |
| Provider webhooks not exposed | Communications/finance | High | Provider contracts were intentionally deferred | Delivery/payment status is not externally authoritative | Add provider-specific signed, replay-safe endpoints when selected | Before provider automation |
| Production observability incomplete | Operations | High | Audit tables exist; monitoring platform does not | Failures may be discovered late | Structured redacted logs, error tracking, alerts and health checks | Before launch |
| Runtime config has development defaults | Configuration | High | Local development convenience | Reset links can use localhost; missing config can fail late | Production-only fail-fast validation | Before launch |
| Remaining npm advisories in tooling | Supply chain | High | Vitest 3 and Prisma CLI transitive dependencies | Test UI/build tooling can be exposed in unsafe environments | Upgrade in isolated maintenance PR; never expose Vitest UI | Before shared dev tooling; production risk assess now |
| Extensive cascade-delete graph | Database | High | Early schema favored parent cleanup | Direct deletion can erase historical learning/audit context | Keep soft-delete workflows; review cascades before delete tooling | Before admin delete features |
| No database/browser/provider integration suite | Testing | High | Tests are predominantly mocked/unit/service | Real schema, cookies, providers and browser behavior remain unproved | Add ephemeral Postgres and Playwright critical journeys | Before scale; manual tests before launch |
| Legacy and central ledgers coexist | Architecture | Medium | Additive migration preserved live behavior | Reporting can choose inconsistent sources | Publish ownership map; reconcile then retire safely | Post-launch controlled work |
| `AUTH_SECRET` and `REDIS_URL` are declared but unused | Configuration | Medium | Deferred signing/shared-rate-limit decisions | Misleading operational setup | Implement intended use or remove from contract | Before security certification |
| No CSP in application config; HSTS edge state unknown | Security | Medium | Basic headers only | Reduced browser exploit containment | Deploy report-only CSP, tune, enforce; verify HSTS at edge | Before broad public traffic |
| Fixed 30-day sessions without idle/device policy | Identity | Medium | Simple opaque session design | Longer exposure after token theft | Define privileged TTL, rotation, session listing/revocation | Near term |
| Retention/privacy policy absent | Governance | Medium | Technical fields exist without approved policy | Over-retention or premature deletion risk | Business/legal policy and scheduled enforcement | Before sensitive data scale |
| No dedicated worker/queue runtime | Automation | Medium | Database outbox foundation only | Processing depends on explicit invocation and single-process limits | Add monitored worker only when event volume requires | Before automation scale |
| Public source images exceed 1 MB | Performance | Low | Launch visuals prioritize fidelity | Mobile transfer/processing cost | Measure, resize and modernize assets | Post-launch measurement |
| Role shells duplicate navigation structure | Frontend | Low | Preserved domain-specific workflows | Higher maintenance cost | Consolidate only around stable shared behavior | Post-launch |
